# v0.1.13 — pysnmp 7.x compatibility: lazy `UdpTransportTarget` + runtime API dispatch

After v0.1.12 shipped, the same `AbstractTransportTarget.__init__()
got multiple values for argument 'timeout'` error started appearing again
on HAOS 2026.x — but this time it was **a different bug**:

```
SNMP client construction failed for 192.168.10.10:161:
AbstractTransportTarget.__init__() got multiple values for argument 'timeout'
SNMP client construction failed for 10.18.176.10:161:
AbstractTransportTarget.__init__() got multiple values for argument 'timeout'
```

The difference: this is not the v0.1.10 `client._target.__class__(...)`
round-trip anymore (v0.1.11 removed it). It's a real upstream API
incompatibility — the user's HAOS is running **pysnmp 7.x**, not
pysnmp 6.x.

## Root cause

HAOS 2026.x ships Python 3.14 with **pysnmp 7.1.29 pre-installed at
the system level** (`/usr/local/lib/python3.14/site-packages/pysnmp/`).
HA Core's dependency resolver doesn't override that system-level
pysnmp with the integration's manifest pin (`pysnmp>=6.2.6,<7.0.0`)
in this configuration — and pysnmp 7.x has a completely incompatible
`UdpTransportTarget.__init__` signature:

| | pysnmp 6.2.6 | pysnmp 7.1.29 |
|---|---|---|
| `UdpTransportTarget.__init__` signature | `(self, transportAddr, timeout=1, retries=5, tagList=b"")` | `(self, timeout=1, retries=5, tagList=b"")` |
| How you build one | `UdpTransportTarget((host, port), timeout=3, retries=2)` | `await UdpTransportTarget.create((host, port), timeout=3, retries=2)` |
| Address attribute name | `transportAddr` | `transport_address` |
| Python support | 3.8 – 3.12 | 3.10 – 3.14 |

The integration was calling the 6.x sync constructor:

```python
UdpTransportTarget((host, port), timeout=3, retries=2)
```

Against pysnmp 7.x's `__init__(self, timeout=1, retries=5, ...)`,
that binds `(host, port)` positionally to `timeout`, then `timeout=3`
collides with it as a keyword → `TypeError: AbstractTransportTarget.__init__()
got multiple values for argument 'timeout'`. Every config-flow connection
test failed. v0.1.11's fix couldn't reach this because the bug was
in the constructor signature itself, not in our use of it.

Confirmed locally by installing pysnmp 7.1.29 in a venv and running
the v0.1.12 code path against it:

```
$ pip install pysnmp==7.1.29
$ python -c "from pysnmp.hlapi.v3arch.asyncio import UdpTransportTarget;
             UdpTransportTarget(('192.168.1.1', 161), timeout=3, retries=2)"
TypeError: AbstractTransportTarget.__init__() got multiple values for argument 'timeout'
```

Exact same TypeError, exact same message format, exact same call site.

## Fix

Two coupled changes — defer `UdpTransportTarget` construction the same
way `SnmpEngine` is deferred (v0.1.12), and dispatch the constructor
call based on a runtime signature inspection so both pysnmp 6.x and
7.x work without forking the code path.

### `custom_components/hikvision_snmp/snmp_client.py`

```python
def _detect_udp_target_api() -> str:
    """Return "v6" or "v7" based on UdpTransportTarget.__init__ signature."""
    import inspect
    sig = inspect.signature(UdpTransportTarget.__init__)
    if "transportAddr" in sig.parameters:
        return "v6"
    return "v7"


_UDP_TARGET_API: str | None = None


def _udp_target_api() -> str:
    """Cached wrapper around _detect_udp_target_api()."""
    global _UDP_TARGET_API
    if _UDP_TARGET_API is None:
        _UDP_TARGET_API = _detect_udp_target_api()
    return _UDP_TARGET_API


async def _build_udp_target(host, port, timeout, retries):
    """Build a UdpTransportTarget against whatever pysnmp version is loaded."""
    api = _udp_target_api()
    if api == "v6":
        # Synchronous 6.x constructor.
        return UdpTransportTarget((host, port), timeout=timeout, retries=retries)
    # Async 7.x classmethod.
    return await UdpTransportTarget.create((host, port), timeout=timeout, retries=retries)


class HikvisionSnmpClient:
    def __init__(self, ...):
        ...
        # SnmpEngine AND UdpTransportTarget are both lazy now.
        self._engine: SnmpEngine | None = None
        self._target: Any | None = None
        ...

    async def _ensure_engine(self) -> SnmpEngine:
        if self._engine is None:
            self._engine = await _get_shared_engine()
        if self._target is None:
            self._target = await _build_udp_target(
                self._host, self._port,
                self._resolved_timeout, self._resolved_retries,
            )
        return self._engine
```

### `custom_components/hikvision_snmp/manifest.json`

```diff
- "requirements": ["pysnmp>=6.2.6,<7.0.0"]
+ "requirements": ["pysnmp>=6.2.6,<8.0.0"]
```

Widen the upper bound so HA's resolver is allowed to pick pysnmp 7.x
when the system-level install is 7.x. Both APIs are now supported
inside the integration via `_build_udp_target`.

## What you should see

For users whose "Failed to connect" was the v0.1.10 / v0.1.13 bug:

- **Before v0.1.13:** config-flow "Test connection" → `cannot_connect:
  Failed to connect` on every device, every install, with the
  `AbstractTransportTarget.__init__() got multiple values for argument
  'timeout'` TypeError in `home-assistant.log`.
- **After v0.1.13:** config-flow "Test connection" succeeds on every
  device the coordinator itself can talk to. The pysnmp 7.x
  `UdpTransportTarget.create(...)` async classmethod is used under
  pysnmp 7.x; the sync 6.x constructor is used under pysnmp 6.x. The
  choice is made once per process via `inspect.signature`.

If the user's pysnmp is *neither* 6.x nor 7.x (some future major
release), `_detect_udp_target_api` falls into the v7 branch and we'll
try `UdpTransportTarget.create(...)`. If that also fails the error
surfaces as a regular `cannot_connect` — the integration no longer
hard-crashes on pysnmp ABI mismatches.

## Why this is the right layer to fix it

Three options considered:

1. **Pin pysnmp to `<7.0.0` harder** (e.g. via `pip install --force-reinstall`)
   — wouldn't help because the system-level pysnmp at
   `/usr/local/lib/python3.14/site-packages/pysnmp/` overrides the
   integration's venv in HAOS's resolution. We can't downgrade the
   system Python install from inside an integration.
2. **Wrap `UdpTransportTarget` in a shim class** that exposes one API
   and translates to whatever pysnmp is installed — same as what
   `_build_udp_target` does, just with more indirection.
3. **Runtime API dispatch based on `inspect.signature`** — what v0.1.13
   does. Minimal indirection, no extra class, the inspector is cached
   once per process so the cost is one-time.

Option 3 was picked because it adds zero abstraction overhead, exposes
the dispatch logic directly where it's needed, and lets future pysnmp
8.x (if it changes the signature again) be supported by adding one
more branch to `_build_udp_target`.

## Tests added (`tests/test_snmp_client.py`)

Six new tests, plus three updated for the new lazy-target contract:

| Test | Asserts |
|---|---|
| `test_target_not_constructed_in_sync_init` | After `HikvisionSnmpClient(...)`, both `client._target` and the module-level engine singleton are still `None`. Pre-v0.1.13 the sync constructor would have built the target and crashed under pysnmp 7.x. |
| `test_pysnmp_v6_api_uses_sync_constructor` | When `_UDP_TARGET_API = "v6"`, `_build_udp_target` uses the sync `UdpTransportTarget((host, port), ...)` path with `timeout`/`retries` kwargs. |
| `test_pysnmp_v7_api_uses_async_create` | When `_UDP_TARGET_API = "v7"`, `_build_udp_target` awaits `UdpTransportTarget.create((host, port), ...)` instead — the pysnmp 7.x API the system-level install requires. |
| `test_detection_picks_v6_when_transportAddr_in_signature` | `_detect_udp_target_api()` returns `"v6"` when the constructor signature has a `transportAddr` parameter (verified by mocking a fake 6.x class). |
| `test_detection_picks_v7_when_transportAddr_missing` | `_detect_udp_target_api()` returns `"v7"` when the constructor signature has only `(timeout, retries, tagList)` — the case that was raising `multiple values for argument 'timeout'` on HAOS 2026.x. |
| `test_engine_and_target_built_in_same_ensure_call` | A single `await _ensure_engine()` populates both `client._engine` and `client._target` (no second helper method to call from the request methods). |
| `test_construct_*` (5 existing tests, updated) | Same as before but drive `await client._ensure_engine()` first since `_target` is now lazy. |

Total test count: **43 passed** (28 helpers + 15 snmp_client).
