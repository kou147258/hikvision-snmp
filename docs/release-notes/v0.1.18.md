# v0.1.18 — IPC `ip_addr` + `subnet_mask` + `gateway` + video codecs

The integration has always queried these OIDs via the `system OID walk`
in `coordinator.py` (they were defined in `const.py:SYSTEM_OIDS` since
v0.1.0), but the matching `HikvisionSensorDescription` entries were
never added to `sensor.py:IPC_SENSORS` — so the integration queried
them and discarded the result. After auditing the maintainer's
`snmpwalk` output against the running integration on real IPC
hardware, five OIDs that returned meaningful values were identified
as missing.

## Symptom

After adding a Hikvision IPC, the integration's device page shows:

- Model, Firmware, MAC, Manufacturer ✓
- CPU Usage, Memory Total/Usage, Storage Total/Used ✓
- Uptime, Device Time, Network Type ✓
- **IP Address — ✗ missing** (NVR shows it, IPC doesn't)
- Subnet Mask — ✗ missing
- Gateway — ✗ missing
- Primary/Secondary Video Codec — ✗ missing

This was an asymmetry bug — `HikvisionSnmpClient._do_get_raw` ran the
walk over `.39165.1.*`, the `decode_walk_results` helper mapped the
results to `identification.{ip_addr,subnet_mask,gateway,
video_codec_primary,video_codec_secondary}`, and the coordinator
shipped the dict to entities, but no `HikvisionSensor` was created
for those keys.

`snmpwalk -v2c -c public <ip> .1.3.6.1.4.1.39165` shows the values
clearly; the integration just wasn't displaying them:

```text
SNMPv2-SMI::enterprises.39165.1.16.0 = IpAddress: 10.18.176.10
SNMPv2-SMI::enterprises.39165.1.17.0 = IpAddress: 255.255.255.0
SNMPv2-SMI::enterprises.39165.1.18.0 = IpAddress: 10.18.176.1
SNMPv2-SMI::enterprises.39165.1.21.0 = STRING: "H.264"
SNMPv2-SMI::enterprises.39165.1.22.0 = STRING: "H.264"
```

## Fix

Add five new `HikvisionSensorDescription` entries to
`sensor.py:IPC_SENSORS`:

| Key | translation_key | Icon | Source OID |
|---|---|---|---|
| `ip_addr` | `ip_addr` (shared with NVR's `ip_addr`) | `mdi:ip` | `.1.3.6.1.4.1.39165.1.16.0` (IpAddress) |
| `subnet_mask` | `subnet_mask` | `mdi:subnet` | `.1.3.6.1.4.1.39165.1.17.0` (IpAddress) |
| `gateway` | `gateway` | `mdi:router-network` | `.1.3.6.1.4.1.39165.1.18.0` (IpAddress) |
| `video_codec_primary` | `video_codec_primary` | `mdi:video-high-definition` | `.1.3.6.1.4.1.39165.1.21.0` (STRING) |
| `video_codec_secondary` | `video_codec_secondary` | `mdi:video-high-definition` | `.1.3.6.1.4.1.39165.1.22.0` (STRING) |

The `ip_addr` translation_key is shared with NVR's existing
`ip_addr` sensor — both display `IP 地址` in zh-locale HA, since
the concept is identical.

### Const.py changes

`const.py:SYSTEM_OIDS` was already correct (the OIDs were always
queried). v0.1.18 just adds inline comments for the OIDs that
weren't documented (`.20 device_type_code`, `.23 media_mode`,
`.26-.28 ptz_status_*` — all Hikvision-internal values that v0.1.18
still doesn't expose, but they're now at least commented in the
constants file so future maintainers don't have to re-audit).

### Translation changes

Both `translations/en.json` and `translations/zh.json` updated:

```jsonc
{
  "entity": {
    "sensor": {
      "subnet_mask":            {"name": "Subnet Mask"},      // "子网掩码"
      "gateway":                {"name": "Gateway"},          // "默认网关"
      "video_codec_primary":    {"name": "Primary Video Codec"}, // "主码流编码"
      "video_codec_secondary":  {"name": "Secondary Video Codec"} // "副码流编码"
    }
  }
}
```

`ip_addr` was already present (used by NVR's `ip_addr` sensor);
the new IPC `ip_addr` reuses the same translation_key. No
duplicate JSON entry needed.

## What you should see

In HA on HAOS 2026.x after upgrading to v0.1.18:

- **Before v0.1.18:** IPC device page showed 13 sensors (Model,
  Device Name, Firmware, MAC, Manufacturer, CPU Usage, Memory Total,
  Memory Usage, Storage Total, Storage Used, Uptime, Device Time,
  Network Type). No network panel info, no video codec info.
- **After v0.1.18:** IPC device page shows 18 sensors. New entries:
  IP Address, Subnet Mask, Gateway, Primary Video Codec, Secondary
  Video Codec. The new IP-related sensors are particularly useful
  for `device-tracker` automations and dashboard network panels.

## Edge cases

- **`ip_addr` may be `0.0.0.0`** on some Hikvision firmware versions
  when the device is in a transitional state (e.g. mid-reboot).
  The integration already handles this via the `if ... else None`
  check in the value extractor — entity goes unavailable, not 0.
- **`.1.13/14/15` (ip_addr_alt1/2/3) are NOT exposed** — they
  return `0.0.0.0` on every IPC in the maintainer's fleet and are
  presumably reserved for future firmware use.
- **`.1.5` (device_count) is NOT exposed** — returns string "88"
  on the maintainer's devices; semantically unclear (channel count?
  device ID?). Documented in `const.py` as `device_count` but not
  exposed as a sensor.
- **`.1.20`, `.1.23`, `.1.26-28`, `.1.30-34`** are NOT exposed —
  Hikvision-internal values with no public MIB documentation.

## Tests

No new tests added. The existing tests in `tests/test_sensor.py`
already cover the IPC sensor tuple via:

- `test_all_static_sensor_translations_have_key` — iterates over
  `IPC_SENSORS` and verifies each has `translation_key == key`.
- `test_translation_keys_covered_in_en_json` /
  `test_translation_keys_covered_in_zh_json` — verifies every
  `translation_key` the platforms reference is present in the
  translation files. Adding 5 new sensors auto-extends the
  iteration; the tests still pass with the same assertions.

Total test count: **66 passed** (unchanged).
