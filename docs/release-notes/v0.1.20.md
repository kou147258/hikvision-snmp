# v0.1.20 — force entity_registry to apply translation_key

After v0.1.19 shipped with `_attr_name = "Model"` etc. (restoring the
v0.1.14 behaviour of always showing an English suffix), users on
zh-locale HA installs continued to see English names like "CPU
Usage" / "Firmware Version" / "IP Address" — because HA's frontend
applies `translation_key` only when the entity's `name` is unset /
overridden, and we were setting `name` to a non-None English string.

This release adds a post-setup hook in `async_setup_entry` that calls
`entity_registry.async_update_entity(entity_id, name=None)` on every
sensor / binary_sensor we just created. Clearing `name` to `None`
forces HA's frontend to consult `translation_key` on the next render
and display the user's locale's translation (e.g. "型号" /
"固件版本" / "IP 地址" for zh-locale users).

Also adds `translations/zh-Hans.json` and `translations/zh-CN.json`
as copies of `zh.json`. The user's HA locale is most likely `zh-Hans`
or `zh-CN` (HA core's `translations/zh-Hans.json` is what's producing
the Chinese header strings they see). Without locale-specific files
in our integration, HA's translation loader falls back to `zh.json` —
which works on most installs, but providing explicit `zh-Hans.json` /
`zh-CN.json` matches the convention used by HA core and removes the
fallback.

## Symptom

After v0.1.19:

- IPC page (18 sensors): every entity showed English suffix
  ("CPU Usage", "Firmware Version", "Device Name", "MAC Address",
  "Manufacturer", "Memory Usage", "Memory Total", "Storage Total",
  "Storage Used", "Uptime", "Device Time", "Network Type", "IP
  Address", "Subnet Mask", "Gateway", "Primary Video Codec",
  "Secondary Video Codec").
- NVR page (9 sensors): same — all English.

User's expectation (zh-locale HA): "型号" / "固件版本" / "CPU 使用率"
/ "内存使用率" / "存储使用率" / "IP 地址" etc.

## Root cause

HA Core 2026.x's entity name resolution for the frontend has
multiple layers:

1. **entity_registry.name** (user override) — if set, this is used
   directly with no translation lookup.
2. **translation_key** lookup in `translations/<lang>.json` — applied
   only if `entity_registry.name` is `None` AND the entity has a
   `translation_key` set.
3. **original_name** / `state.name` — fallback when translation
   fails.

The v0.1.19 release had `entity_description.name = "Model"` and
`self._attr_name = "Model"`, which HA's framework copied into
`entity_registry.name` at registration. With `entity_registry.name`
set, HA skipped the `translation_key` lookup and rendered "Model"
directly.

For the binary sensors (`Online` / `Recording`), the same
`translation_key` machinery was bypassed by the same mechanism —
the `name` field was set on the entity class as `_attr_name =
"Online"` and the framework copied that to the registry, blocking
the translation lookup.

## Fix

Two changes:

### 1. `async_setup_entry` post-setup hook — clear `entity_registry.name`

```python
async_add_entities(entities)

# v0.1.20 — force entity_registry to re-derive entity names from
# translation_key by clearing the cached ``name`` field.
from homeassistant.helpers import entity_registry as _er

registry = _er.async_get(hass)
for entity in entities:
    try:
        if entity.entity_id:
            registry.async_update_entity(entity.entity_id, name=None)
    except Exception:  # noqa: BLE001
        pass
```

Same hook is added to `binary_sensor.py:async_setup_entry` for the
two binary sensors (`Online`, `Recording`).

When `entity_registry.name` is `None`, HA's frontend consults the
entity's `translation_key` for display. The translation_key is
present in the registry (set automatically by HA's framework from
`entity_description.translation_key` at registration time). The
frontend's translation loader picks the right `translations/<lang>.json`
file based on the user's locale, and translates the entity name
accordingly.

### 2. Locale-specific translation files

Added two new files to `custom_components/hikvision_snmp/translations/`:

- `zh-Hans.json` (Simplified Chinese, content = same as `zh.json`)
- `zh-CN.json` (China, content = same as `zh.json`)

Both are byte-identical copies of `zh.json`. The reason for the
duplication: HA's translation loader tries `translations/<lang>.json`
where `<lang>` matches the user's exact locale (e.g. `zh-Hans`,
`zh-CN`). If our integration only provides `zh.json`, the loader
falls back to it but only after exhausting the locale-specific
search. Adding `zh-Hans.json` and `zh-CN.json` matches HA core's
file naming convention and ensures the translation lookup succeeds on
the first try for the most common Chinese locales.

## Edge cases / fallbacks

- **HA wasn't able to find the user's locale-specific translation
  file**: even without `zh-Hans.json` / `zh-CN.json` (only the older
  `zh.json` was there), HA's translation loader should fall back to
  `zh.json`. Adding the locale-specific files just removes the
  fallback path's edge cases.

- **HA's `entity_registry.name` was already set by a previous
  integration version** (e.g. v0.1.19 set `_attr_name = "Model"` and
  HA's framework copied that to the registry): v0.1.20's post-setup
  hook clears the registry's `name` field on every entity the
  integration owns, so even upgrading from v0.1.19 (without a
  delete + re-add) should now apply the translations. No need to
  delete the entry — just update + restart.

- **User-renamed entities**: if the user previously renamed an
  entity in HA's UI (e.g. to a custom name like "Front Door Camera
  Model"), v0.1.20's `name=None` will clear that custom name and
  revert to the translated version. This is a one-time cost; users
  can re-rename after the upgrade.
