# v0.1.14 — pysnmp 7.x renamed `getCmd`/`bulkCmd`/`nextCmd` too; runtime resolver

After v0.1.13 shipped, HA users running HAOS 2026.x hit a brand-new
symptom when adding the integration:

```
无法加载配置向导: {"message":"Invalid handler specified"}
```

HA couldn't load the config flow at all. v0.1.13's runtime
`UdpTransportTarget` dispatch fix made the test pass on pysnmp 7.x in
isolation, but the integration still couldn't load.

## Root cause

The previous version fixed the **runtime** pysnmp 7.x ABI break
(`UdpTransportTarget.__init__` signature change), but missed a second
ABI break at **module load time**:

```python
# custom_components/hikvision_snmp/snmp_client.py (pre-v0.1.14)
from pysnmp.hlapi.asyncio import (
    CommunityData,
    ContextData,
    ObjectIdentity,
    ObjectType,
    SnmpEngine,
    UdpTransportTarget,
    UsmUserData,
    bulkCmd,    # ← ImportError on pysnmp 7.x (renamed to bulk_cmd)
    getCmd,     # ← ImportError on pysnmp 7.x (renamed to get_cmd)
    nextCmd,    # ← ImportError on pysnmp 7.x (renamed to next_cmd)
    ...
)
```

pysnmp 7.x renamed the cmd request functions from camelCase to
snake_case, in addition to the `UdpTransportTarget` constructor change:

| | pysnmp 6.x | pysnmp 7.x |
|---|---|---|
| GET request | `UdpTransportTarget`-then-`getCmd` | `UdpTransportTarget.create`-then-`get_cmd` |
| BULK walk | `UdpTransportTarget`-then-`bulkCmd` | `UdpTransportTarget.create`-then-`bulk_cmd` |
| NEXT walk | `UdpTransportTarget`-then-`nextCmd` | `UdpTransportTarget.create`-then-`next_cmd` |

The `from pysnmp.hlapi.asyncio import bulkCmd, getCmd, nextCmd` statement
in our `snmp_client.py` raises `ImportError: cannot import name 'bulkCmd'`
at module load time on pysnmp 7.x. HA's integration loader catches the
`ImportError`, refuses to register the integration, the `ConfigFlow`
class never gets registered, and HA surfaces "Invalid handler
specified" when the user clicks "Add Integration".

This is the same situation as v0.1.10's
`AbstractTransportTarget.__init__() got multiple values for argument
'timeout'` — a name the legacy integration code expects that the
upstream library no longer provides — except this one fires earlier
(at import, not at request time) and prevents the integration from
loading at all.

Confirmed locally:

```
$ pip install pysnmp==7.1.29
$ python -c "from pysnmp.hlapi.asyncio import bulkCmd, getCmd, nextCmd"
ImportError: cannot import name 'bulkCmd' from 'pysnmp.hlapi.asyncio'
```

## Fix

Apply the same runtime-dispatch pattern v0.1.13 used for
`UdpTransportTarget` to the cmd functions. Don't put them in the
`from pysnmp.hlapi.asyncio import ...` statement at all — resolve at
runtime via a small helper that tries each naming convention in order
until one matches.

### `custom_components/hikvision_snmp/snmp_client.py`

```python
# Module-load-time import: only the names that exist under BOTH
# pysnmp 6.x and 7.x. The version-sensitive cmd functions are NOT
# imported here — see _resolve_cmd_functions below.
from pysnmp.hlapi.asyncio import (
    CommunityData, ContextData, ObjectIdentity, ObjectType,
    SnmpEngine, UdpTransportTarget, UsmUserData,
    usm3DESEDEPrivProtocol, usmAesCfb128Protocol, ...,
)
import pysnmp.hlapi.asyncio as _pysnmp_hlapi


def _resolve_cmd_functions():
    """Resolve get/bulk/next cmd function names across pysnmp major versions.

    Returns (get_cmd, bulk_cmd, next_cmd) as a tuple of callables, using
    whichever naming convention the loaded pysnmp exposes:

    - pysnmp 6.x: camelCase — getCmd, bulkCmd, nextCmd
    - pysnmp 7.x: snake_case — get_cmd, bulk_cmd, next_cmd

    Tries camelCase first (legacy), then snake_case. Raises ImportError
    with an actionable message if neither variant is found.
    """
    variants = (
        ("getCmd", "bulkCmd", "nextCmd"),     # pysnmp 6.x
        ("get_cmd", "bulk_cmd", "next_cmd"),  # pysnmp 7.x
    )
    for variant in variants:
        if all(hasattr(_pysnmp_hlapi, name) for name in variant):
            return tuple(getattr(_pysnmp_hlapi, name) for name in variant)
    raise ImportError(
        "Could not locate get/bulk/next cmd functions in pysnmp.hlapi.asyncio; "
        "tried camelCase (pysnmp 6.x) and snake_case (pysnmp 7.x). If a "
        "future pysnmp release renamed them again, add another variant to "
        "_resolve_cmd_functions()."
    )


getCmd, bulkCmd, nextCmd = _resolve_cmd_functions()
```

The rest of `snmp_client.py` is untouched. The internal references
(`getCmd(...)`, `bulkCmd(...)`, `nextCmd(...)`) keep their camelCase
spelling — they just resolve to whichever spelling the loaded pysnmp
exposes.

## What you should see

In HA on HAOS 2026.x after upgrading to v0.1.14:

- **Before v0.1.14:** "Add Integration → Hikvision SNMP" → config-flow
  loader raises `ImportError: cannot import name 'bulkCmd'` → HA
  surfaces "无法加载配置向导: Invalid handler specified" and the
  integration never appears in the "Discovered" / "Add new" list.
- **After v0.1.14:** config-flow loader succeeds, "Add Integration →
  Hikvision SNMP" shows the 3-step form (User / SNMP / Confirm),
  connection test runs the v0.1.13 lazy target + runtime API dispatch
  path under pysnmp 7.x, devices come online.

In HA on HAOS 2025.x or earlier with pysnmp 6.x:

- **Before v0.1.14:** works fine (camelCase names resolve).
- **After v0.1.14:** also works fine — `_resolve_cmd_functions` picks
  the camelCase variant first, same callables as before, no behaviour
  change.

## Why this is the right layer to fix it

Three options considered:

1. **Catch ImportError at HA load time and try the snake_case variant
   in a fallback module** — adds a second module file, requires HA to
   know which one to load, splits the integration surface across two
   files. Ugly.
2. **Re-import the cmd functions inside each call site using
   `getattr(_hlapi, "get_cmd", _hlapi.getCmd)`** — works but adds
   repeated branching at every request site (3 places in this file:
   `_do_get_raw`, `_do_bulk`, `_walk_next`).
3. **Resolve once at module load via a helper, expose `getCmd` /
   `bulkCmd` / `nextCmd` as module-level bindings** — what v0.1.14
   does. One branch point, the rest of the file is untouched, future
   pysnmp 8.x just needs another tuple added to the variants list.

Option 3 mirrors v0.1.13's `UdpTransportTarget` fix pattern (one
runtime dispatch, no abstraction indirection, no per-call-site
branching) and keeps the integration source readable.

## Tests added (`tests/test_snmp_client.py`)

Four new tests, all passing:

| Test | Asserts |
|---|---|
| `test_cmd_functions_resolve_to_camelcase_under_pysnmp_v6` | When `_pysnmp_hlapi` exposes `getCmd`/`bulkCmd`/`nextCmd`, the resolver returns the camelCase variants. The path pysnmp 6.x hits. |
| `test_cmd_functions_resolve_to_snakecase_under_pysnmp_v7` | When `_pysnmp_hlapi` exposes `get_cmd`/`bulk_cmd`/`next_cmd` instead, the resolver returns the snake_case variants. The path HAOS 2026.x hits under pysnmp 7.1.29. |
| `test_cmd_functions_raise_when_no_variant_found` | When neither variant exists (some future pysnmp 8.x that renamed again), `_resolve_cmd_functions` raises `ImportError` with a message that mentions `_resolve_cmd_functions` — so the next maintainer knows exactly where to add a new variant. |
| `test_module_does_not_eagerly_import_camelcase_cmd_names` | Headline regression guard — the module must NOT eagerly import the camelCase names. If a future refactor reintroduces `from pysnmp.hlapi.asyncio import bulkCmd, ...` at the top, this test fails (because the test file itself can't import the module to call the resolver). |

Total test count: **47 passed** (28 helpers + 19 snmp_client).
