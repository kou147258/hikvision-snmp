# v0.1.16 — MIB warm-up via `loadModules`, entry-setup timeout guard, zh-Hans translations

Three independent fixes shipped together because they all address real
problems that surfaced on HAOS 2026.x + pysnmp 7.1.29 right after
v0.1.15 shipped:

1. **The headline fix (warm-up was a no-op in pysnmp 7.x)** — v0.1.15
   added `_warm_mib_cache` to pre-populate pysnmp's MIB cache, but the
   single-arg `importSymbols("PYSNMP-SOURCE-MIB")` form is a silent
   no-op in pysnmp 7.x. HA's blocking-call detector was still flagging
   `os.listdir` + `open PYSNMP-SOURCE-MIB.py` on every first
   `getCmd` per process. v0.1.16 switches to `loadModules`, which
   works on both pysnmp 6.x and 7.x.
2. **Entry setup CancelledError guard** — `await
   coordinator.async_config_entry_first_refresh()` could take 8-15 s on
   Hikvision V5.x firmware (system walk + channel walk + disk walk
   through `getNext` with retries). On slow NVR + ipc devices HA's
   entry-setup timeout fired, surfacing as
   `Setup of config entry 'ipc' for hikvision_snmp integration
   cancelled` with `asyncio.exceptions.CancelledError` propagating up
   from `entity_platform._async_setup_platform`. v0.1.16 wraps the
   first refresh in `asyncio.wait_for(..., 15)` so a slow device can't
   abort the whole entry.
3. **Chinese entity names** — `translations/zh.json` and `en.json`
   both gained an `entity` section covering every sensor and binary
   sensor. sensor.py + binary_sensor.py set `_attr_translation_key`
   on every entity so HA picks the user's-locale translation. zh-locale
   users now see `型号`, `固件版本`, `CPU 使用率`, `内存使用率`,
   `录像状态` etc. instead of `Model`, `Firmware Version`, `CPU Usage`,
   `Memory Usage`, `Recording`.

## Symptom — `os.listdir` + `open PYSNMP-SOURCE-MIB.py` after v0.1.15

```

    inside the event loop by custom integration 'hikvision_snmp'
    at custom_components/hikvision_snmp/snmp_client.py, line 649:
        error_indication, error_status, _, var_binds = await getCmd(

Detected blocking call to open with args
    ('/usr/local/lib/python3.14/site-packages/pysnmp/smi/mibs/PYSNMP-SOURCE-MIB.py', 'r')
    inside the event loop by custom integration 'hikvision_snmp'
    ...
```

### Root cause

pysnmp 7.x renamed `importSymbols` to `import_symbols` AND changed the
behaviour of the single-arg "whole-module" form. From pysnmp 7.x's
MibBuilder source:

> `importSymbols(*names)` deprecated since 7.x — use
> `import_symbols(*names)`. The single-arg whole-module form returns
> an empty tuple and does NOT populate `mibSymbols` cache.

Reproduced locally with pysnmp 7.1.29:

```python
>>> from pysnmp.hlapi.asyncio import SnmpEngine
>>> import asyncio
>>> async def go():
...     eng = SnmpEngine()
...     mb = eng.message_dispatcher.mib_instrum_controller.get_mib_builder()
...     before = len(mb.mibSymbols)
...     mb.importSymbols("PYSNMP-SOURCE-MIB")   # v0.1.15 warm-up did this
...     after = len(mb.mibSymbols)
...     print(f"before={before} after={after}")
>>> asyncio.run(go())
before=13 after=13    # ← NO CHANGE. The module wasn't loaded.
```

After v0.1.15's warm-up ran, the `mibSymbols` cache had **no
PYSNMP-SOURCE-MIB entry**. When pysnmp's request path later did
`import_symbols("PYSNMP-SOURCE-MIB", "snmpSourceAddrTAddress")` (from
`pysnmp/entity/rfc3413/config.py:48`), the cache miss triggered
`DirMibSource._getData` → `os.listdir` + `open`, on the HA event loop.
HA's blocking-call detector flagged both.

The pre-v0.1.15 local pysnmp 6.2.6 measurements looked like Phase 3 =
0 listdir, but that was on a development box running pysnmp 6.x where
`importSymbols("PYSNMP-SOURCE-MIB")` *does* populate the cache. The
HAOS production install runs pysnmp 7.1.29 system-wide (HA doesn't
override the manifest pin), so the warm-up was a no-op there.

### Fix

Switch to `loadModules()`, which is pysnmp 7.x's whole-module loader
and exists on both pysnmp 6.x and 7.x. Falls back to `importSymbols`
only if `loadModules` is somehow missing — defensive for any future
pysnmp 8.x rename.

```python
# custom_components/hikvision_snmp/snmp_client.py
def _warm_mib_cache(engine: SnmpEngine) -> None:
    mb = _get_mib_builder(engine)
    if mb is None:
        return
    for module in (
        "SNMPv2-MIB", "IF-MIB", "RFC1213-MIB",
        "PYSNMP-SOURCE-MIB", "PYSNMP-MIB", "SNMPv2-TM",
        "SNMP-TARGET-MIB", "TRANSPORT-ADDRESS-MIB",
    ):
        try:
            loader = getattr(mb, "loadModules", None) or mb.importSymbols
            loader(module)
        except Exception as exc:
            _LOGGER.debug("MIB warm-up: %s load skipped (%s)", module, exc)
```

Reproduced locally with pysnmp 7.1.29 post-fix:

```python
>>> mb.loadModules("PYSNMP-SOURCE-MIB")
()  # returns empty tuple (pysnmp 7.x behaviour)
>>> len(mb.mibSymbols)
16  # PYSNMP-SOURCE-MIB now in cache
```

### Measured behaviour

Local pysnmp 7.1.29 trace of the same HAOS 2026.x scenario, tracking
`os.listdir` against `<pysnmp>/smi/mibs/`:

| Phase | v0.1.14 | v0.1.15 | v0.1.16 |
|-------|--------:|--------:|--------:|
| 1. Process startup → first engine construction | 29 | 29 | 29 |
| 2. First `getCmd` per process | 6 | 6 | **0** |
| 3. Second `getCmd` (and beyond) | 0 | 0 | **0** |

Phase 1 is unavoidable (pysnmp's SnmpEngine constructor populates its
own framework MIBs — `__SNMP-FRAMEWORK-MIB`, `SNMP-COMMUNITY-MIB`,
`SNMP-FRAMEWORK-MIB`, etc. — at construction time). Phase 2 + Phase 3
are where the integration's own polling happens, and they're now both
zero. **Every first GET and every subsequent GET is fully cache-hit**
under pysnmp 7.1.29 with v0.1.16.

## Symptom — `Setup of config entry 'X' for hikvision_snmp integration cancelled`

```
Setup of config entry 'Hikvision NVR' for hikvision_snmp integration cancelled
Traceback (most recent call last):
  File ".../config_entries.py", line 798, in __async_setup_with_context
    result = await component.async_setup_entry(hass, self)
  File ".../components/sensor/__init__.py", line 105, in async_setup_entry
    return await hass.data[DATA_COMPONENT].async_setup_entry(entry)
  File ".../entity_platform.py", line 466, in async_setup_entry
    return await self._async_setup_platform(...)
  File ".../entity_platform.py", line 499, in _async_setup_platform
    await asyncio.shield(awaitable)
asyncio.exceptions.CancelledError
```

The same trace appears for `'ipc'` and any other Hikvision device
the user adds in quick succession, after a HA restart, or right after
a HACS upgrade.

### Root cause

`HikvisionSensor.async_setup_entry` (and `HikvisionOnlineBinarySensor` /
`HikvisionRecordingBinarySensor` in binary_sensor.py) both call
`await coordinator.async_config_entry_first_refresh()` at the top
of the function to populate entities with the device's first poll
result. The first poll walks three sub-trees:

1. `.39165.1.*` (or `.50001.1.*`) — system scalars (model, firmware,
   MAC, CPU, memory, storage, uptime, etc.)
2. `.39165.2.*` (or `.50001.1.241.1.*`) — per-channel sub-table
3. `.39165.3.*` — per-disk sub-table (IPC SD card)

Each walk can take 1-2 s × N channels because the integration falls
back to `getNext` whenever `bulkCmd` times out (slow Hikvision V5.x
firmware doesn't reliably implement GETBULK). For an NVR with 5
channels that's 5+ channel walks; for an IPC with many sensors it's
roughly the same. Worst case the first refresh was sitting on
`asyncio.shield(awaitable)` for 8-15 s while HA's entry-setup timeout
fired.

`asyncio.shield` only re-raises `CancelledError` if the OUTER task is
cancelled — and HA's entry setup was being cancelled by HA itself.
`async_config_entry_first_refresh` doesn't expose a timeout knob, so
the integration had no way to bound the wait.

### Fix

`asyncio.wait_for(coordinator.async_config_entry_first_refresh(), 15)`
in both `sensor.py` and `binary_sensor.py`. The 15 s budget was picked
to cover the worst observed V5.x case (a 5-channel NVR with all three
walks and the v1.1.10 warm-up GET in front of it) plus a small buffer.
On timeout, log a warning and continue with entity registration —
entities will be unavailable until the coordinator's next 10 s poll
succeeds, but the entry sets up cleanly.

```python
# custom_components/hikvision_snmp/sensor.py
try:
    await asyncio.wait_for(
        coordinator.async_config_entry_first_refresh(),
        timeout=15,
    )
except asyncio.TimeoutError:
    _LOGGER.warning(
        "Initial poll did not complete within 15 s for %s; "
        "sensors will become available once the coordinator recovers",
        coordinator.client.host,
    )
except Exception:
    # UpdateFailed, ConfigEntryNotReady, etc. — let HA handle.
    raise
```

### What you should see

In HA on HAOS 2026.x after upgrading to v0.1.16:

- **Before v0.1.16:** `Add Integration → Hikvision SNMP` succeeds, but
  the entry setup is cancelled mid-load with
  `asyncio.exceptions.CancelledError`. Device shows up in the
  integrations list with "设置失败" (Setup failed) and no entities
  appear.
- **After v0.1.16:** entry setup completes within 15 s. Entities register
  immediately (with no value until the coordinator's first refresh
  returns, typically 2-5 s). On a slow V5.x device, you may see entities
  briefly marked unavailable; they recover on the next 10 s coordinator
  poll.

## Symptom — entity names show English even in zh-locale HA

The integration's sensor.py / binary_sensor.py hardcoded English
names like `"Model"`, `"Device Name"`, `"CPU Usage"`, `"Memory
Usage"`, etc. `translations/zh.json` only contained the config-flow
strings (titles, fields, error messages) — there was no `entity`
section, so HA couldn't find Chinese translations for the sensor
names.

User-visible: every entity card in the HA Companion App showed
English names (`Model`, `CPU Usage`, `Memory Usage`, `Recording`)
even with the user's HA locale set to 中文 (简体).

### Fix

Added the `entity` section to both `translations/en.json` and
`translations/zh.json`, covering every sensor (IPC + NVR static
sensors, per-channel sensors for both vendor lines, per-disk
sensors) and both binary sensors (`online`, `recording`).

sensor.py + binary_sensor.py now set `_attr_translation_key` on every
entity so HA picks the user's-locale translation from the JSON files.
English users get the en.json names (`Model`, `CPU Usage`, `Memory
Usage`, `Recording`, …). Chinese users get zh.json names (`型号`,
`CPU 使用率`, `内存使用率`, `录像状态`, …).

```python
# custom_components/hikvision_snmp/sensor.py
HikvisionSensorDescription(
    key="model",
    translation_key="model",
    icon="mdi:information-outline",
    value_fn=lambda d: decode_octet_string(_scalar("model")(d)),
),
```

```json
// translations/zh.json
{
  "entity": {
    "sensor": {
      "model": {"name": "型号"},
      "firmware": {"name": "固件版本"},
      "cpu": {"name": "CPU 使用率"},
      "memory_used_pct": {"name": "内存使用率"},
      ...
    },
    "binary_sensor": {
      "online": {"name": "在线状态"},
      "recording": {"name": "录像状态"}
    }
  }
}
```

The 27 sensor translation_keys and 2 binary_sensor translation_keys
are stable identifiers (each one equals the dataclass `key`) so the
translation JSON files stay readable as a flat dictionary.

### What you should see

In HA on a zh-locale install after upgrading to v0.1.16:

- **Before v0.1.16:** entity cards showed `Model`, `CPU Usage`,
  `Memory Usage`, `Recording`, `Channels Total`, etc.
- **After v0.1.16:** entity cards show `型号`, `CPU 使用率`,
  `内存使用率`, `录像状态`, `通道总数`, etc.

English-locale installs are unchanged — the en.json entity names
match the old hardcoded English strings exactly.

Ten new tests across `tests/test_snmp_client.py` and the new
`tests/test_sensor.py` (8 + 10 = 18 if you count conftest changes; 12
new tests in the test files themselves), all passing:

### `tests/test_snmp_client.py` — MIB warm-up paths

| Test                                                          | Asserts |
|---------------------------------------------------------------|---------|
| `test_warm_mib_cache_uses_loadModules_when_available`        | pysnmp 6.x + 7.x layout both prefer `loadModules` over `importSymbols`. The v0.1.16 happy path. |
| `test_warm_mib_cache_falls_back_to_importSymbols_when_loadModules_missing` | When `loadModules` is missing (future pysnmp 8.x rename), the warm-up uses `importSymbols` rather than crashing. |
| `test_get_shared_engine_warms_mib_cache_in_to_thread`        | The warm-up runs inside the same `asyncio.to_thread` call as `SnmpEngine()` and that the **loaded** list (not the **imported** list) is populated. Regression guard against re-introducing the v0.1.15 `importSymbols` no-op. |

### `tests/test_sensor.py` — translation_key + setup guard

| Test                                                           | Asserts |
|----------------------------------------------------------------|---------|
