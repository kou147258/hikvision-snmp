# v0.1.10 — Warm-up GET + lenient timeout in connection test

Two changes to `_test_connection` in `config_flow.py`, both learned from
the [OtisPresley/snmp-switch-manager](https://github.com/OtisPresley/snmp-switch-manager)
reference integration's `async_initialize` pattern.

## Change 1 — Warm-up GET

The first GET on a freshly constructed `pysnmp` `SnmpEngine` triggers
lazy init of message compilation, transport dispatcher, etc.
Measurably slower than subsequent GETs (typically 100–500 ms extra on a
busy HA host). The integration now does a **throwaway warm-up GET** to
the standard MIB-II scalar `sysUpTime` (`.1.3.6.1.2.1.1.3.0`) before the
real vendor-MIB probe:

```python
try:
    await client.get("1.3.6.1.2.1.1.3.0")  # sysUpTime
except Exception as exc:
    _LOGGER.debug("warm-up GET failed (ignored): %s", exc)
```

The warm-up response is **discarded**. Its only purpose is to flush
pysnmp's internal state so the subsequent vendor-MIB GET runs at
steady-state speed.

## Change 2 — Connection-test timeout: 1 s / 1 retry → 3 s / 2 retries

Hikvision V5.x firmware responds in 200–500 ms when idle, but can take
1–3 s when the video pipeline is busy (encoding H.265, recording,
streaming). Combined with pysnmp's first-request init overhead, the
previous 1 s + 1 retry = 2 s budget was tight against the worst case.

```python
client._target = client._target.__class__(
    (host, port), timeout=3, retries=2,
)
```

The connection-test target is built with this longer timeout; the
long-lived coordinator client uses the production defaults (1 s /
1 retry) so steady-state polling stays responsive.

## Combined effect

| Scenario | v0.1.9 behaviour | v0.1.10 behaviour |
|----------|------------------|------------------|
| Device is fine, pysnmp is fast | PASS in ~50 ms | PASS in ~100 ms (warm-up) |
| Device busy, first request slow | FAIL (1 s timeout) | PASS (3 s timeout absorbs init + busy) |
| Device SNMP daemon off / wrong community | FAIL | FAIL (warm-up also fails — same root cause) |
| Extended MIB disabled on Hikvision device | FAIL on first GET | Warm-up succeeds (standard MIB), still FAIL on vendor MIB — root cause unchanged |

The third row confirms that **a real network/credential fault still
surfaces as the proper `cannot_connect` error**, not a hidden failure.

## What you should see

If your previous "Failed to connect" was actually the first-request init
race (more common on HA hosts where the integration is loaded on every
restart), v0.1.10 should now succeed.

If your "Failed to connect" persists after upgrading to v0.1.10, the root
cause is **not** pysnmp init — it's either:

- The Hikvision device's **"Extended MIB" / "私有 MIB"** toggle is off
  (vendor OIDs return `NoSuchInstance` while standard MIB-II OIDs
  respond fine — your other SNMP integrations on switches won't catch
  this because they read standard MIBs).
- The community string isn't actually `public` on the device you're
  testing.
- A VLAN firewall is silently dropping UDP/161 between HA's VLAN and
  the device's VLAN, even though ICMP/TCP pass.

The one-line diagnostic that resolves the ambiguity (run it from the
HAOS host shell):

```bash
apk add net-snmp-tools
snmpget -v2c -c public -t 3 192.168.10.10 1.3.6.1.4.1.50001.1.3.0
```

Three possible results:

| Output | Root cause | Fix |
|---|---|---|
| `STRING: "..."` | pysnmp init (now fixed by warm-up) — try v0.1.10 | nothing else needed |
| `Timeout: No Response` | VLAN UDP/161 firewall or device SNMP off | check router firewall + device web UI |
| `No Such Instance` | Extended MIB disabled on the device | enable in device web UI |
| `Unknown user name` | community string is not `public` | use the actual community |
