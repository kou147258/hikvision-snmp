# v0.1.23 — per-channel / per-disk entities added by coordinator listener after first poll

After v0.1.22 dropped the `wait_for(..., 15s)` guard, entity_platform
setup completed in < 1 s and no HA "Setup taking over 10 seconds"
warnings fired. But this introduced a side effect: per-channel and
per-disk entities depended on `coordinator.data` being populated
(it carries the walk results), which doesn't happen until the first
successful poll. On busy V5.x devices where the first poll exceeds
the entity_platform setup budget, those entities were skipped during
the initial pass — the user had to reload the integration to get
them.

v0.1.23 fixes this by splitting entity creation into two phases:

1. **System entities** (model, CPU, memory, IP, etc.) — no data
   dependency, registered immediately. Always present.
2. **Per-channel + per-disk entities** — depend on `coordinator.data`.
   - **Phase 2 (immediate best-effort):** if `coordinator.data` is
     already populated at setup time (first poll raced ahead), register
     the dynamic entities right away.
   - **Phase 3 (deferred via coordinator listener):** if `coordinator.data`
     is `None` at setup time, register a one-shot listener that fires
     after the first successful refresh. The listener adds the dynamic
     entities as soon as data is available.

The listener is **idempotent** — it uses a flag
(`coordinator._hikvision_dynamic_entities_added`) to be a no-op on
subsequent fires, so the per-channel entities are only added once.

## Symptom

After v0.1.22, the user reported (on a busy V5.x IPC where the first
poll > 10 s) that the system entities (CPU Usage, Memory Usage,
Storage Total/Used, IP Address, etc.) appeared, but per-channel and
per-disk entities were missing. Reloading the integration added them
back, but that required user intervention.

## Root cause

The v0.1.22 design registered all entities in a single pass:

```python
data = coordinator.data or {}  # None on first setup if poll hasn't run
entities = []
for desc in NVR_SENSORS:    # system entities — always added
    entities.append(HikvisionSensor(...))
for ch_idx in data.get("channels", {}).get("name", {}).keys():  # empty if data is None
    entities.append(HikvisionChannelSensor(...))  # never added
async_add_entities(entities)
```

When `coordinator.data` is `None` at setup time (the normal case on
busy devices), the per-channel / per-disk loops iterate over an empty
dict and add no entities. The system entities are unaffected (they
don't iterate over `data`).

The user has to wait for the first poll to complete (could be 10-30 s
on a busy device), then reload the integration so `async_setup_entry`
runs again with `coordinator.data` populated. This is annoying UX.

## Fix

v0.1.23 splits entity creation into two phases and uses a
`DataUpdateCoordinator` listener to handle the late-data case:

```python
async def async_setup_entry(hass, entry, async_add_entities):
    coordinator = hass.data[DOMAIN][entry.entry_id]

    # Phase 1: system entities — no data dependency, always added
    system_entities = [HikvisionSensor(coordinator, entry, desc) for desc in NVR_SENSORS or IPC_SENSORS]
    async_add_entities(system_entities)
    # (v0.1.20 entity_registry hook to clear name field for translation)
    ...

    # Phase 2: best-effort per-channel / per-disk from current data
    _maybe_add_dynamic_entities(hass, entry, coordinator, async_add_entities)

    # Phase 3: register a coordinator listener for late data
    if not getattr(coordinator, "_hikvision_dynamic_entities_added", False):
        coordinator.async_add_listener(
            _make_listener(hass, entry, coordinator, async_add_entities)
        )


def _maybe_add_dynamic_entities(...):
    """Idempotent: if data is None OR already added, no-op."""
    if getattr(coordinator, "_hikvision_dynamic_entities_added", False):
        return
    if coordinator.data is None:
        return
    # ... build per-channel + per-disk entities ...
    coordinator._hikvision_dynamic_entities_added = True
    async_add_entities(dynamic)
    # (v0.1.20 entity_registry hook to clear name field for translation)
    ...


def _make_listener(...):
    async def _on_coordinator_update():
        if getattr(coordinator, "_hikvision_dynamic_entities_added", False):
            return
        if coordinator.data is None:
            return
        _maybe_add_dynamic_entities(...)
    return _on_coordinator_update
```

`DataUpdateCoordinator.async_add_listener(listener)` is an HA Core
2024+ API that registers a callback fired after every successful
refresh. The listener is added once per coordinator (per entry) and
the flag prevents duplicate entity registration.

## What you should see

In HA on a busy V5.x device after upgrading to v0.1.23:

- **Before v0.1.23 (v0.1.22 state):** system entities appear
  immediately, per-channel / per-disk entities are missing until
  the user reloads the integration. "Missing" until reload.
- **After v0.1.23:** system entities appear immediately (as before).
  Per-channel / per-disk entities appear as soon as the coordinator's
  first poll completes (typically 10-30 s after entry setup on a
  busy device). No user intervention required. Subsequent polls
  re-fire the listener but the flag short-circuits to a no-op.

The user can now go from "device added → 0 entities → 30s wait →
reload → 18 entities" to "device added → 18 system entities → 30s
wait → 16 channel entities" with no reload needed.

## Edge cases

- **First poll fails** (e.g. network blip): the listener doesn't fire
  (the listener is only called after successful updates). The flag
  stays False. On the next successful poll, the listener fires and
  the dynamic entities are added. If the first poll never succeeds,
  the dynamic entities are never added — same behaviour as v0.1.22.
  A user-triggered reload still works (it's a full `async_setup_entry`
  pass with `coordinator.data` populated from the latest successful
  poll).
- **Multiple setup_entry calls** (e.g. on reload): each call
  re-registers a listener, but the old listener is also still
  registered (HA doesn't auto-unregister). The flag prevents
  duplicate entity registration — both listeners see the flag set
  to True after the first one runs, so the second is a no-op. The
  minor cost is that the old listener is called on every coordinator
  update and short-circuits immediately. Not a correctness issue.
- **HA restart**: listeners are in-memory. After HA restart, the
  coordinator is recreated (no listener state persisted), so the
  first setup_entry call after restart registers a fresh listener
  and the flag starts at False again. Normal flow.
