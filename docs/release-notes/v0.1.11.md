# v0.1.11 — Fix `AbstractTransportTarget.__init__() got multiple values for argument 'timeout'` in connection test

A real-world bug surfaced after v0.1.10 shipped. Users upgrading saw
the integration's config-flow "Test connection" step fail with the
following in `home-assistant.log`:

```
custom_components.hikvision_snmp.config_flow: SNMP client construction
failed for 10.18.176.10:161:
AbstractTransportTarget.__init__() got multiple values for argument 'timeout'
```

…which surfaced to the UI as `cannot_connect: Failed to connect`. v0.1.10's
intention (lenient 3 s / 2 retries connection-test budget) was correct,
but the way it tried to apply that budget was wrong. This release fixes it
without losing the v0.1.10 intent.

## Root cause

v0.1.10 added this block right after constructing the client:

```python
client._target = client._target.__class__(
    (host, port), timeout=3, retries=2,
)
```

The idea was to swap the client's `UdpTransportTarget` for one with the
longer connection-test timeout — the long-running polling client (built
later by the coordinator) would carry the production 1 s / 1 retry defaults.

The problem: `client._target.__class__` round-trip is **not a stable
abstraction boundary** in pysnmp 6.x. The MRO of `UdpTransportTarget`
is `UdpTransportTarget → AbstractTransportTarget → object`, and the
two `__init__` signatures aren't always identical across pysnmp 6.x
point releases. On the builds HAOS pulls in (and on any pysnmp version
that wires the parent `__init__` differently than 6.2.6), the
`__class__((host, port), timeout=3, retries=2)` call resolves to the
wrong `__init__` and Python raises:

```
TypeError: AbstractTransportTarget.__init__() got multiple values for
argument 'timeout'
```

The exception was caught by the surrounding `try/except` in
`_test_connection`, logged as `"SNMP client construction failed for
…: …"`, and the function returned `(None, "")`, which the config flow
rendered as `cannot_connect`. So every device, on every install, looked
unreachable — even though the integration was perfectly capable of
talking to it the moment the entry was created and the coordinator
took over with its own correctly-built target.

## Fix

Stop rebuilding `client._target` via `__class__` at all. Route
`timeout` and `retries` through `HikvisionSnmpClient.__init__` and
build the `UdpTransportTarget` with the right values **once**, at
construction time. This is a one-line refactor of the wrong line plus
a small constructor signature change.

### `custom_components/hikvision_snmp/snmp_client.py`

`HikvisionSnmpClient.__init__` accepts two new optional kwargs:

```python
def __init__(
    self,
    host: str,
    port: int = DEFAULT_PORT,
    version: str = "v2c",
    auth: dict[str, str] | None = None,
    timeout: float | None = None,
    retries: int | None = None,
) -> None:
    ...
    self._target = UdpTransportTarget(
        (host, port),
        timeout=timeout if timeout is not None else DEFAULT_REQUEST_TIMEOUT,
        retries=retries if retries is not None else DEFAULT_RETRIES,
    )
```

`None` (not `DEFAULT_REQUEST_TIMEOUT`) is used as the default sentinel
so callers that pass `timeout=None` explicitly get the production
default — important because the config flow previously built its
client with the default and then **swapped** the target in-place; now
the config flow just builds the client with the values it wants from
the start.

### `custom_components/hikvision_snmp/config_flow.py`

```python
# before (v0.1.10 — buggy)
client = HikvisionSnmpClient(host=host, port=port, version=version, auth=auth)
...
client._target = client._target.__class__(
    (host, port), timeout=3, retries=2,
)

# after (v0.1.11 — correct)
client = HikvisionSnmpClient(
    host=host, port=port, version=version, auth=auth,
    timeout=3, retries=2,
)
```

The warm-up GET (`sysUpTime`), the three-layer `try/except`, and the
IPC-root → NVR-root fallback all stay exactly as v0.1.10 left them.
Only the timeout-application mechanism changes.

## What you should see

For users whose "Failed to connect" was the v0.1.10 bug:

- **Before:** config-flow "Test connection" → `cannot_connect: Failed to connect`
  on every device, every install, with the `AbstractTransportTarget.__init__()
  got multiple values for argument 'timeout'` error in `home-assistant.log`.
- **After v0.1.11:** config-flow "Test connection" succeeds on every device
  the coordinator itself can talk to, because the client is now built with
  the right timeout/retries from the start.

For users whose "Failed to connect" was a real network or credential fault
(extended MIB off, wrong community, VLAN firewall), v0.1.11 changes nothing
— the diagnostic matrix in `docs/release-notes/v0.1.10.md` still applies
unchanged.

## Why this isn't v0.1.10's last version

The three previous connection-test hardening releases (v0.1.8 → v0.1.10)
all landed in quick succession in response to the same observable symptom
("Failed to connect" reported from HA), with each release exposing the
next underlying defect. v0.1.11 closes that loop: the symptom is now
traceable to a real, named, code-level bug with a verifiable fix, and
five new unit tests pin the contract so a future refactor can't silently
re-introduce the `__class__` round-trip.

## Tests added (`tests/test_snmp_client.py`)

Five new tests, all passing:

| Test | Asserts |
|---|---|
| `test_construct_with_default_timeout_and_retries` | `_target.timeout == DEFAULT_REQUEST_TIMEOUT` and `_target.retries == DEFAULT_RETRIES` when caller doesn't pass overrides |
| `test_construct_with_explicit_timeout_and_retries` | `_target.timeout == 3 and _target.retries == 2` when caller passes `timeout=3, retries=2` — the path the config-flow now uses |
| `test_construct_with_only_timeout` | Overriding only `timeout` leaves `retries` at the production default |
| `test_construct_with_only_retries` | Overriding only `retries` leaves `timeout` at the production default |
| `test_construct_does_not_raise_abstract_transport_target_error` | Regression guard — constructing with explicit kwargs succeeds without raising; this is the exact scenario v0.1.10's `__class__` patch failed on |

Total test count: **33 passed** (28 helpers + 5 snmp_client).
