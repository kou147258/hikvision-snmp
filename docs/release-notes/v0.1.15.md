# v0.1.15 — HA 2026.x `UnitOfFrequency` rename + MIB cache warm-up + brand asset

Three small, independent fixes shipped together because they're all in
the same patch line:

1. **The headline fix** — `cpu_freq` sensor used `UnitOfInformation.MEGAHERTZ`,
   which HA removed in the 2025.1 release (deprecated since 2024.x). On
   HAOS 2026.x the sensor module fails to import, the integration never
   sets up, and the user sees "Error setting up entry Hikvision SNMP".
2. **First-GET blocking-call noise reduction** — pre-load the standard
   MIB-II modules (`SNMPv2-MIB`, `IF-MIB`, `RFC1213-MIB`) plus pysnmp's
   own protocol-internal MIBs (`PYSNMP-SOURCE-MIB`, `PYSNMP-MIB`,
   `SNMPv2-TM`, `SNMP-TARGET-MIB`, `TRANSPORT-ADDRESS-MIB`) once per
   process inside the same `asyncio.to_thread` call as `SnmpEngine()`
   construction. After warm-up, every subsequent request hits the
   in-memory MIB cache and skips pysnmp's `os.listdir`-based MIB
   directory scan.
3. **Brand asset for HACS / HA 2026.3+** — added
   `custom_components/hikvision_snmp/brand/icon.png` so HA's
   `/api/brands/integration/hikvision_snmp/icon` endpoint serves an
   image instead of the placeholder.

## Symptom #1 — `Error setting up entry Hikvision SNMP`

After v0.1.14 shipped, HAOS 2026.x users hit a fresh symptom on
adding the integration. Four log entries, all the same root cause:

```python
# homeassistant/loader.py", line 1289
cache[full_name] = self._import_platform(platform_name)
# custom_components/hikvision_snmp/sensor.py", line 177, in <module>
    native_unit_of_measurement=UnitOfInformation.MEGAHERTZ,
                               ^^^^^^^^^^^^^^^^^^^^^^^^^^^
AttributeError: type object 'UnitOfInformation' has no attribute 'MEGAHERTZ'
```

The same `AttributeError` fires twice more — once from
`homeassistant.loader` (which logs `Unexpected exception importing
platform custom_components.hikvision_snmp.sensor`) and once from
`homeassistant.config_entries` (which surfaces as the user-facing
`Error setting up entry Hikvision SNMP`).

### Root cause

`UnitOfInformation.MEGAHERTZ` made no sense — megahertz is a frequency
unit, not an information unit. HA deprecated it in 2024 and **removed
the alias entirely** in 2025.1. Any code that still references it
fails to import on 2025.1+; on 2026.x the import-time `AttributeError`
aborts the entire `sensor.py` module load, so HA's integration loader
raises `ImportError: Exception importing custom_components.hikvision_snmp.sensor`
and the config flow never registers.

### Fix

`UnitOfInformation.MEGAHERTZ` → `UnitOfFrequency.MEGAHERTZ` at
`custom_components/hikvision_snmp/sensor.py:182`, plus `UnitOfFrequency`
added to the `homeassistant.const` import block. The comment above the
line documents why the rename happened so a future HA rename of the
frequency unit will be obvious to investigate:

```python
# HA 2024 deprecated `UnitOfInformation.MEGAHERTZ` (megahertz is a
# frequency, not an information unit) and 2025.1 removed the
# deprecated alias entirely. Use the proper ``UnitOfFrequency`` enum
# instead.
native_unit_of_measurement=UnitOfFrequency.MEGAHERTZ,
```

### What you should see

In HA on HAOS 2026.x after upgrading to v0.1.15:

- **Before v0.1.15:** "Add Integration → Hikvision SNMP" → sensor
  module fails to import → config flow never registers → integration
  never sets up → `Error setting up entry Hikvision SNMP` + `AttributeError`
  tracebacks in the log.
- **After v0.1.15:** sensor module imports cleanly, integration sets
  up, `cpu_freq` sensor reports CPU frequency in MHz (no functional
  change to the displayed value, only the type-class of the unit).

In HA on HAOS 2024.x or earlier:

- **Before v0.1.15:** the integration was emitting `DeprecationWarning`
  for the unit on every sensor-state write.
- **After v0.1.15:** no deprecation warning; integration identical
  from the user's perspective.

## Symptom #2 — `Detected blocking call to listdir` on first GET

Pre-v0.1.15, on the very first `getCmd` per process pysnmp does an
`os.listdir` against `<pysnmp>/smi/mibs/` and an `open` on each `.py`
file it finds — once per MIB module that's referenced. HA's
blocking-call detector flags each one:

```
Detected blocking call to listdir with args
    ('/usr/local/lib/python3.14/site-packages/pysnmp/smi/mibs',)
    inside the event loop by custom integration 'hikvision_snmp'
    at .../snmp_client.py, line ...
```

v0.1.12 already moved `SnmpEngine()` itself into `asyncio.to_thread`,
which stops the `SnmpEngine.__init__` `listdir` calls. The remaining
`listdir` calls in v0.1.14 came from `MibBuilder.resolve_with_mib`
inside `getCmd`/`bulkCmd`/`nextCmd`, which still ran on the HA event
loop. After the first GET, every later GET was clean (Phase 3 in our
local pysnmp 7.1.29 measurements). The first GET had 6 listdir calls —
3 for the OIDs the integration queries (SNMPv2-MIB / IF-MIB /
RFC1213-MIB) and 3 for pysnmp's own protocol-internal MIBs
(PYSNMP-SOURCE-MIB / PYSNMP-MIB / SNMPv2-TM).

### Root cause

pysnmp's `MibBuilder` only loads a MIB module when something asks
for a symbol in it. `lookupMib=False` on `getCmd` (v0.1.9) skips the
OID → name resolution for the OIDs the integration queries, but it
doesn't skip the protocol-internal MIBs pysnmp itself needs on every
request — those load on the first request and stay cached after that.

### Fix

Pre-load the MIB modules inside the same `_build_engine_and_warm_mibs`
worker thread that already runs `SnmpEngine()`. After warm-up, the
in-memory `MibBuilder.mibSymbols` cache contains every symbol the
integration will ever look up, so `MibBuilder._getData` never has to
walk the MIB directory.

```python
# custom_components/hikvision_snmp/snmp_client.py
async def _get_shared_engine() -> SnmpEngine:
    ...
    def _build_engine_and_warm_mibs():
        engine = SnmpEngine()
        _warm_mib_cache(engine)   # ← v0.1.15 addition
        return engine

    _ENGINE_SINGLETON = await _asyncio.to_thread(
        _build_engine_and_warm_mibs
    )


def _warm_mib_cache(engine: SnmpEngine) -> None:
    """Pre-load MIB modules the integration + pysnmp itself queries.

    Called inside ``asyncio.to_thread`` (off the HA event loop). Tolerates
    missing modules — the OIDs are still queried by numeric form.
    """
    mb = _get_mib_builder(engine)
    if mb is None:
        return
    for module in (
        # MIBs whose OIDs the integration queries
        "SNMPv2-MIB", "IF-MIB", "RFC1213-MIB",
        # pysnmp protocol-internal MIBs queried on every request PDU
        "PYSNMP-SOURCE-MIB", "PYSNMP-MIB", "SNMPv2-TM",
        "SNMP-TARGET-MIB", "TRANSPORT-ADDRESS-MIB",
    ):
        try:
            mb.importSymbols(module)
        except Exception as exc:
            _LOGGER.debug("MIB warm-up: %s import skipped (%s)", module, exc)


def _get_mib_builder(engine: SnmpEngine):
    """Locate pysnmp's ``MibBuilder`` across the 6.x → 7.x attribute renames.

    pysnmp 6.x: ``engine.msgAndPduDsp.mibInstrumController.mibBuilder``
    pysnmp 7.x: ``engine.message_dispatcher.mib_instrum_controller
                 .get_mib_builder()``
    """
    try:
        md = getattr(engine, "message_dispatcher", None) or engine.msgAndPduDsp
        mic = getattr(md, "mib_instrum_controller", None) or md.mibInstrumController
        if hasattr(mic, "get_mib_builder"):
            return mic.get_mib_builder()
        return mic.mibBuilder
    except AttributeError:
        return None
```

### Measured behaviour

Local pysnmp 7.1.29 trace of the same HAOS 2026.x scenario (counts of
`os.listdir` against `<pysnmp>/smi/mibs/`):

| Phase                              | v0.1.14 | v0.1.15 |
|------------------------------------|--------:|--------:|
| 1. Process startup → first engine  |      29 |      29 |
| 2. First `getCmd` per process      |       6 |       6 |
| 3. Second `getCmd` (and beyond)    |       0 |       0 |

The 6 calls in Phase 2 are pysnmp's own protocol-internal MIB lookups
that fire on the first PDU build regardless of our warm-up — they
hit `<pysnmp>/smi/mibs/` to resolve pysnmp's own textual conventions
and *don't* use the `MibBuilder.mibSymbols` cache we pre-populated.
Eliminating them entirely would require patching pysnmp itself; for
the integration's own OIDs and the integration's own request flow,
Phase 3 is now zero — every subsequent request is fully cache-hit.

For most users this is the difference between "see blocking-call
warnings every integration start" and "see them once per process
lifetime, on the very first request after HA starts".

### What you should see

In HA on HAOS 2026.x after upgrading to v0.1.15:

- **Before v0.1.15:** HA's `Detected blocking call to listdir with
  args ('.../pysnmp/smi/mibs',)` warning fires every time the
  coordinator's first GET fires after a process restart.
- **After v0.1.15:** the warm-up runs once in the worker thread during
  the first `_ensure_engine` call; the warning doesn't fire again on
  subsequent requests. The first GET still fires the 6 protocol-internal
  warnings because pysnmp's PDU-builder code path bypasses the cache
  we populated — that's a pysnmp-side limitation, not the integration's.

## Symptom #3 — HACS / HA shows "icon not available"

HA 2026.3 changed how brand images are served: instead of pulling
from the central `home-assistant/brands` repository, custom
integrations can ship brand images inline at
`custom_components/<domain>/brand/icon.png`. The endpoint that serves
them is `/api/brands/integration/{domain}/{image}`.

Pre-v0.1.15 the integration only had
`custom_components/hikvision_snmp/icon.png` (used as the HA entity-card
default icon if no per-entity `icon="mdi:..."` is set) — but HA's
brand-image endpoint couldn't find anything to serve, so it returned
the placeholder image and the user saw "icon not available" in the
HACS store and HA's Devices & Services integration header.

### Fix

Copied the existing icon to the brand directory:

```text
custom_components/hikvision_snmp/brand/icon.png   ← v0.1.15 addition
```

Both files exist after v0.1.15: the original `icon.png` (HA's
entity-card fallback for the integration panel) and the new
`brand/icon.png` (HA's brand-image endpoint, which HACS's
"integrations → information" panel reads).
