# v0.1.12 — Defer SnmpEngine construction to `asyncio.to_thread`; share one engine across every client

A second class of "Failed to connect" surfaced after v0.1.11 shipped. The
config-flow connection test no longer crashes with the
`AbstractTransportTarget.__init__() got multiple values for argument 'timeout'`
TypeError, but `home-assistant.log` started showing a new diagnostic from
HA's event-loop blocking-call monitor:

```
Detected blocking call to listdir with args
    ('/usr/local/lib/python3.14/site-packages/pysnmp/smi/mibs',)
inside the event loop by custom integration 'hikvision_snmp'
at custom_components/hikvision_snmp/snmp_client.py, line 100:
    self._engine = SnmpEngine()

Detected blocking call to open with args
    ('/usr/local/lib/python3.14/site-packages/pysnmp/smi/mibs/PYSNMP-SOURCE-MIB.py', 'r')
inside the event loop by custom integration 'hikvision_snmp'
at custom_components/hikvision_snmp/snmp_client.py, line 100:
    self._engine = SnmpEngine()
```

v0.1.12 fixes this without losing any of v0.1.10 / v0.1.11's behaviour.

## Root cause

`pysnmp.hlapi.asyncio.SnmpEngine.__init__` does *not* take an
`lookupMib=False` parameter, and the constructor itself calls
`importSymbols("__SNMP-FRAMEWORK-MIB", ...)` synchronously to seed engine
state — that import walks `<pysnmp>/smi/mibs/`, calls
`os.listdir()` (for case-sensitivity) and `open()` on each candidate
file, all synchronously, all on the thread that's constructing the
engine.

In HA's event-loop model, *every* line of code in an async function runs
on the event loop unless explicitly dispatched to a worker thread via
`asyncio.to_thread(...)` (or `loop.run_in_executor(...)`). So
`HikvisionSnmpClient.__init__` running synchronously on the event-loop
thread and calling `SnmpEngine()` is a violation by HA's policy, and the
two blockers above get flagged. The actual SNMP request itself
(`getCmd` / `bulkCmd` / `nextCmd` with `lookupMib=False`, fixed in
v0.1.9) doesn't trigger this — only the engine constructor does.

The blocking call is also pre-loop:

- `SnmpEngine()` does **not** bind to the asyncio loop — the
  `transportDispatcher` attribute is left `None` and only lazy-created
  on the first `getCmd` / `bulkCmd` / `nextCmd` (which always run in
  the HA event loop).
- That means it's safe to construct the engine inside a worker thread
  via `asyncio.to_thread` — there's no event-loop-affinity to break.

## Fix

Two coupled changes:

1. **Defer engine construction** to the first request via
   `_ensure_engine()` on each client. This pushes the synchronous
   `SnmpEngine()` call off the event-loop thread, so HA's monitor
   stops flagging it.

2. **Share one `SnmpEngine` across every `HikvisionSnmpClient` in the
   process.** The engine construction costs ~430 ms (one-time, off-loop
   now, but still real). Sharing means an N-device integration pays
   that cost once instead of N times. It's safe to share because
   per-request state (`transport_target`, `UsmUserData` /
   `CommunityData`, request IDs) is keyed on the request arguments, not
   on engine state — different hosts go to different
   `UdpTransportTarget` instances.

### `custom_components/hikvision_snmp/snmp_client.py`

```python
# Module-level singleton + lazy-init lock
_ENGINE_SINGLETON: SnmpEngine | None = None
_ENGINE_INIT_LOCK: "asyncio.Lock | None" = None

async def _get_shared_engine() -> SnmpEngine:
    """Return the process-wide SnmpEngine, constructing it on first use."""
    import asyncio as _asyncio
    global _ENGINE_SINGLETON, _ENGINE_INIT_LOCK
    if _ENGINE_SINGLETON is not None:
        return _ENGINE_SINGLETON
    if _ENGINE_INIT_LOCK is None:
        _ENGINE_INIT_LOCK = _asyncio.Lock()
    async with _ENGINE_INIT_LOCK:
        if _ENGINE_SINGLETON is None:
            _ENGINE_SINGLETON = await _asyncio.to_thread(SnmpEngine)
    return _ENGINE_SINGLETON


class HikvisionSnmpClient:
    def __init__(self, ...):
        ...
        # Was: self._engine = SnmpEngine()
        self._engine: SnmpEngine | None = None
        ...

    async def _ensure_engine(self) -> SnmpEngine:
        if self._engine is None:
            self._engine = await _get_shared_engine()
        return self._engine

    async def _do_get_raw(self, var_binds_in):
        await self._ensure_engine()        # ← NEW
        ...

    async def _do_bulk(self, base_oid, max_repetitions):
        await self._ensure_engine()        # ← NEW
        ...

    async def _walk_next(self, oid_root):
        await self._ensure_engine()        # ← NEW
        ...

    async def close(self) -> None:
        # Was: self._engine.closeDispatcher()
        # Now: no-op. Closing one client's dispatcher would tear down
        # the dispatcher for all other clients sharing the engine.
        return None
```

The three `await self._ensure_engine()` call sites are the only places
that touch `self._engine` directly; they're all in front of an actual
`getCmd` / `bulkCmd` / `nextCmd` call. Every public method (`get`,
`get_with_retry`, `get_raw`, `walk`) funnels into one of these three
low-level methods, so lazy init is transparent to callers — no changes
needed in `config_flow.py` or `coordinator.py`.

## What you should see

In `home-assistant.log` after upgrading:

- **Before:** repeated
  `Detected blocking call to listdir/open ... at custom_components/hikvision_snmp/snmp_client.py:100: self._engine = SnmpEngine()`
  warnings every time a config-flow connection test runs or a
  coordinator polls a device for the first time.
- **After v0.1.12:** no `listdir` / `open` blocking-call warnings from
  `hikvision_snmp`. One-time `pysnmp SnmpEngine singleton constructed`
  DEBUG line on the very first request — that's the lazy init, off
  the event loop.

The same blocking-call monitor also flags the unrelated
[`snmp_printer`](https://github.com/dsorlov/snmp_printer) integration
in the log excerpt above (`custom_components/snmp_printer/snmp_client.py:237:
errorIndication, errorStatus, errorIndex, varBinds = await get_cmd(...)`).
That bug is in `snmp_printer`'s `get_cmd` call (no `lookupMib=False` and
no engine-sharing), not in `hikvision_snmp` — v0.1.12 doesn't fix it,
but the fix pattern is the same one this release applies here.

## Why this is the right layer to fix it

There are three options for dealing with the synchronous MIB-directory
FS scan inside `SnmpEngine.__init__`:

1. **Disable MIB loading entirely** — pysnmp 6.x has no clean knob for
   this. The constructor unconditionally calls
   `importSymbols("__SNMP-FRAMEWORK-MIB", ...)` to seed engine state;
   without that, `snmpEngineMaxMessageSize` and `snmpEngineBoots`
   don't get set.
2. **Mock `pysnmp.smi.builder`'s `_getData` / `_listdir`** — fragile,
   breaks on every pysnmp point release.
3. **Run the constructor off the event loop** — what v0.1.12 does.
   Clean, doesn't depend on pysnmp internals, and the engine doesn't
   bind to the loop until later anyway.

Option 3 is the only one that keeps the integration working with
unmodified upstream pysnmp, which is what the manifest pin
(`pysnmp>=6.2.6,<7.0.0`) is meant to allow.

## Tests added (`tests/test_snmp_client.py`)

Four new tests, all passing:

| Test | Asserts |
|---|---|
| `test_engine_not_constructed_in_sync_init` | After `HikvisionSnmpClient(...)`, both `client._engine` and `client_mod._ENGINE_SINGLETON` are still `None`. Pre-v0.1.12 the sync constructor would have built the engine and populated the module singleton. |
| `test_engine_lazy_init_runs_in_to_thread` | The first `_ensure_engine()` call dispatches `SnmpEngine()` through `asyncio.to_thread` (verified by patching it and observing the call) rather than building the engine synchronously on the event-loop thread. |
| `test_clients_share_one_engine_singleton` | Two `HikvisionSnmpClient` instances constructed against different hosts end up with `c1._engine is c2._engine` after each calls `_ensure_engine` — one engine for the whole process. |
| `test_close_is_noop_and_does_not_tear_down_shared_dispatcher` | `await client.close()` does **not** call `closeDispatcher()` on the shared engine. Pre-v0.1.12, calling `close()` would have cleared the dispatcher attribute on the shared singleton and broken every other client. |

Total test count: **37 passed** (28 helpers + 9 snmp_client).
